# Установка и настройка виртуальной машины

## 1 Параметры стенда

Создать Linux VM в VirtualBox: Ubuntu Server 24.04 LTS либо согласованный Debian, 4 vCPU, 8 ГБ RAM, динамический диск 40 ГБ. Скачивать ISO с официального сайта дистрибутива и сверять SHA-256. Включить аппаратную виртуализацию хоста. Установить ОС штатным установщиком; пользователь `labadmin` получает sudo, прямой вход root отключён. После установки выполнить обновления и создать снимок `base-os`.

Для учебного обмена удобны два интерфейса: NAT для загрузки пакетов и host-only для связи с хостом. Не применять bridge без необходимости. IP, маска и шлюз берутся из фактической сети; вымышленные адреса не записываются в системную конфигурацию. Проверки: `ip -brief address`, `ip route`, `resolvectl status`. При использовании NAT можно оставить Web-порты доступными только внутри VM и работать её браузером или SSH-туннелем.

```bash
sudo apt update
sudo apt install -y git curl ca-certificates openssl bash coreutils findutils gawk
git --version
uname -a
```

Docker Engine и Compose plugin устанавливаются по официальной инструкции для выбранного дистрибутива: [Ubuntu](https://docs.docker.com/engine/install/ubuntu/) или [Debian](https://docs.docker.com/engine/install/debian/). Проверки: `docker --version`, `docker compose version`, `docker info`. Пользователь Docker получает фактически административные возможности; в учебной VM можно использовать отдельную учётную запись или `sudo docker`. Сценарии предполагают, что `docker info` уже доступен текущему пользователю.

Гостевые дополнения VirtualBox устанавливают для совпадающей версии гипервизора, при необходимости общих папок и изменения разрешения. Исходники лучше хранить внутри Linux-файловой системы: общий каталог Windows может изменять права и окончания строк.

## 2 Пользователи по ролям методички

Каждый участник воспроизводит установку VM или документирует согласованное использование общей VM. DevOps создаёт четыре Linux-учётные записи: три участника и отдельную техническую учётную запись Git. ФИО не подставляются вымышленно.

```bash
sudo adduser student_a
sudo adduser student_b
sudo adduser student_c
sudo adduser --disabled-password --gecos 'Учебный Git-сервис' gitservice
```

Пароли интерактивные и не сохраняются в отчёте. Учётная запись `gitservice` не является четвёртым участником команды. Назначать sudo всем пользователям не требуется. Для общего репозитория применяют отдельную группу и ограниченные права, для повседневной разработки — личные клоны.

## 3 Передача проекта и проверка

Скопировать каталог `2lab` в Linux VM с сохранением структуры; затем `bash setup.sh --with-redmine`. Для доступа с Windows к сервисам, слушающим localhost VM, можно использовать SSH-туннель:

```bash
ssh -L 8082:127.0.0.1:8082 -L 8085:127.0.0.1:8085 student_a@VM_ADDRESS
```

`VM_ADDRESS` заменяется фактическим IP host-only-интерфейса. После подготовки среды сделать снимок `lab2-tools` при штатно остановленной VM либо при согласованной консистентной процедуре. Снимок VM удобен для восстановления среды, но не заменяет резервную копию базы.

## 4 Критерии готовности

VM загружается, доступна сеть и DNS, системные часы корректны, существуют четыре учётные записи, Git работает, Compose запускает отдельный проект ЛР №2, Redmine доступен, секреты отсутствуют в Git. Фактический запуск VM и настройки GUI должны быть подтверждены собственными снимками, а не скопированными примерами.

## 5 Фактически проверенная Linux-среда

На компьютере запущена установленная Ubuntu 24.04.1 в WSL 2, ядро 5.15.167.4-microsoft-standard-WSL2. Docker Desktop 4.67.0 использует Linux Engine 29.3.1. WSL 2 применяет управляемую виртуальную машину; окна создания VirtualBox VM и её снимки в этом запуске не воспроизводились. Инструкции выше сохраняют отдельный вариант VirtualBox из методички. Подменять его вымышленными снимками нельзя.

Сценарий `sudo bash provision_users.sh` создаёт student_a, student_b, student_c и gitservice, группу supermarket36 и общий bare-репозиторий `/srv/supermarket36/repository.git`. Новые записи не получают sudo и сохраняют закрытый парольный вход. Для личного интерактивного входа участник устанавливает пароль или свой SSH-ключ; проверка выполнялась root через runuser.

`sudo bash verify_git.sh` проверяет три клона, push, feature/develop/release/main, учебный конфликт и тег v1.0.0. В каждой записи Git доверяет только точному пути учебного репозитория через safe.directory. Все автоматически созданные коммиты имеют автора Lab automation. Они демонстрируют механизм, а не имитируют личную работу участников.
