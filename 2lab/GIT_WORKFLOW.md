# Git Flow для учебного проекта

## 1 Модель веток

`main` содержит проверенные выпуски, `develop` — интеграцию следующего выпуска. Рабочие ветки: `codex/feature/SM-xx-name`, стабилизация — `codex/release/1.0.0`, срочные исправления — `codex/hotfix/1.0.1`. Префикс `codex/` не меняет семантику Git Flow. Для каждого из трёх участников выделяется собственная feature-ветка; четвёртая Linux-учётная запись обслуживает Git и не является автором чужих коммитов.

В ЛР №1 коммитятся документы и модели. В ЛР №2 добавляются инфраструктура и управление проектом. Только в ЛР №3 появляется прикладной код. ЛР №4 добавляет независимую утилиту. Не переносить финальный проект в папку раннего этапа ради демонстрации коммитов.

## 2 Инициализация и персональная настройка

```bash
git init -b main
git config user.name 'Фактическое имя участника'
git config user.email 'Фактический адрес участника'
git add README.md .gitignore .gitattributes 1lab
git commit -m 'docs: концепция и модели варианта 36'
git switch -c develop
git switch -c codex/feature/SM-04-environment
git add 2lab
git commit -m 'chore: подготовить окружение ЛР2; refs SM-04'
```

Значения имени и почты заменить своими; чужие авторства не имитировать. Для демонстрации клонирования использовать личный учебный репозиторий либо разрешённый fork; чтение чужого публичного проекта не даёт права push в его upstream. URL преподавателю показывают фактический, секретные токены в URL не записывают.

```bash
git clone ACTUAL_REPOSITORY_URL
git remote -v
git fetch origin
git switch develop
git switch -c codex/feature/SM-05-redmine
```

## 3 Работа с задачей

Перед изменением исполнитель переводит задачу в «В работе». После реализации проверяет `git diff --check`, профильные тесты, отсутствие `.env` и дампов в staged diff. Commit содержит проектный ключ; после импорта Redmine можно использовать `refs #ACTUAL_ID`. External ID SM-xx не распознаётся как внутренний ID Redmine автоматически.

Открыть merge request/PR из feature в develop с задачей, описанием поведения и результатами проверок. Другой участник проводит ревью. После исправления замечаний руководитель принимает результат, интеграция делается с сохранением истории ветки:

```bash
git switch develop
git merge --no-ff codex/feature/SM-05-redmine
git log --graph --decorate --oneline --all
```

Не делать force-push в общие ветки. Rebase допустим в личной ещё не принятой ветке по договорённости. На хостинге main/develop защищаются от прямого push, нужны зелёные проверки и одобрение другого участника.

## 4 Release и hotfix

```bash
git switch develop
git switch -c codex/release/1.0.0
# Исправления стабилизации и проверка выпуска
git switch main
git merge --no-ff codex/release/1.0.0
git tag -a v1.0.0 -m 'Учебный выпуск 1.0.0'
git switch develop
git merge --no-ff codex/release/1.0.0
```

Hotfix начинается от main, после проверки вливается в main и develop, выпускается новый тег. Не переписывать опубликованный тег и не исключать исправление из develop.

## 5 Учебный конфликт и откат

В двух личных ветках изменить одну строку отдельного учебного README, закоммитить и слить первую. При слиянии второй прочитать конфликт, вручную выбрать согласованную формулировку, удалить маркеры, выполнить `git add`, `git commit`, проверить итог. Для прекращения незавершённого merge — `git merge --abort`; для отмены опубликованного изменения — `git revert COMMIT_ID`, а не reset общей истории.

В отчёте показать фактические `status`, `log --graph` и согласованное разрешение конфликта. Снимки и commit ID заранее не выдумываются. Настройка внешнего удалённого репозитория зависит от предоставленного пользователем URL; материалы не утверждают, что публикация уже выполнена.
