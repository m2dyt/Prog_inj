# Настройка Redmine для проекта супермаркета

## 1 Развёртывание

Простой воспроизводимый способ: `bash setup.sh --with-redmine` из `2lab`. Контур `supermarket-redmine` содержит Redmine и собственную PostgreSQL; прикладная БД супермаркета здесь не используется. Сценарий автоматически вызывает redmine/bootstrap.rb: создаёт закрытый проект, участников, трекеры, роли, переходы, пользовательские поля, версию, 15 задач из CSV и связи зависимостей. Пароль admin сразу заменяется случайным из REDMINE_ADMIN_PASSWORD в .env. Пользователи student_a/b/c получают пароли STUDENT_A/B/C_PASSWORD. Повторный запуск сохраняет задачи и существующие пароли; отправка почты выключена.

Для роли специалиста по ИС требуется объяснить детальную установку из методички: зависимости Ruby и Bundler, отдельная БД и пользователь, `config/database.yml`, `bundle install`, секрет сеансов, `RAILS_ENV=production bundle exec rake db:migrate`, загрузка базовых настроек, права на `files`, `log`, `tmp`, запуск приложения и reverse proxy. В Docker эти этапы выполняет официальный образ; протоколировать версии и журналы его инициализации. Если преподаватель требует именно ручную установку без контейнерного образа, выполнить её на отдельном снимке VM по [официальной инструкции](https://www.redmine.org/projects/redmine/wiki/RedmineInstall), используя требования версии, а не устаревшие версии из примера 2021 года.

В комплект включена небольшая тема supermarket. В Redmine 6.1 её каталог монтируется в themes/supermarket, затем bootstrap выбирает тему. Путь public/themes из старых версий больше не применяется. Изменения касаются цветов и оформления карточки задачи. Источник: [официальное описание тем Redmine 6](https://www.redmine.org/projects/redmine/wiki/HowTo_create_a_custom_Redmine_theme).

## 2 Проект и участники

Создать закрытый проект «Информационная система супермаркета — вариант 36», идентификатор `supermarket-36`. Включить задачи, учёт времени, документы, Wiki и репозиторий. Создать пользователей `student_a`, `student_b`, `student_c`; A — Кочетков Роман; B — Энгельгард Кирилл; C — Прохоров Максим. Глобальная административная запись не применяется для обычной работы с задачами.

Таблица 1 — Ролевая модель проекта

| Роль | Права | Ограничения |
|---|---|---|
| Руководитель проекта | Создание и приоритизация задач, назначение исполнителя, версии, подтверждение результата, чтение времени | Глобальное администрирование Redmine не требуется |
| Специалист по ИС | Чтение проекта, создание задач, редактирование задач проекта, файлы, Wiki, комментарии, учёт времени, ревью | Не менять состав участников и глобальные роли |
| DevOps-инженер | Задачи инфраструктуры, репозиторий, сборка, документы, учёт времени, ревью | Не выдавать себе глобальные права |
| Наблюдатель | Чтение задач, Wiki и документов | Нет изменений и учёта от чужого имени |

Назначения: A — руководитель; B — специалист по ИС; C — DevOps. Роли учебной команды не совпадают с ролями manager/cashier/auditor будущего приложения.

## 3 Трекеры, статусы и workflow

Трекеры: `Требование`, `Задача`, `Ошибка`. Категории: `Анализ`, `Инфраструктура`, `Backend`, `Frontend`, `База данных`, `Автоматизация`, `Проверка`. Версия `1.0 Учебный выпуск` содержит все 15 задач.

Статусы: `Новая`, `В работе`, `На проверке`, `Возвращена`, `Закрыта`, `Отклонена`. Последние два закрытые. Для трекера «Ошибка» описание обязательно содержит воспроизведение, ожидаемое и фактическое поведение; для остальных — требование и критерий приёмки.

Таблица 2 — Разрешённые переходы

| Откуда → куда | Исполнитель | Проверяющий | Руководитель |
|---|---|---|---|
| Новая → В работе | Да, своя задача | Нет | Да |
| В работе → На проверке | Да | Нет | Да |
| На проверке → Возвращена | Нет | Да | Да |
| Возвращена → В работе | Да | Нет | Да |
| На проверке → Закрыта | Нет для своего результата | Да | Да |
| Новая → Отклонена | Нет | Нет | Да, с обоснованием |
| Закрыта → Возвращена | Нет | Да, с дефектом | Да |

Настроить матрицу в Администрирование → Workflow отдельно для каждой пары роль/трекер. Условия «своя задача» проверять опциями автора/исполнителя, где они доступны, и политикой ревью. Redmine не гарантирует запрет самоприёмки только наличием столбца «проверяющий»: для строгого технического разделения назначают отдельную роль проверяющего, иначе это организационное правило. В закрытые статусы запрещён прямой переход из «В работе».

## 4 Импорт 15 задач

`backlog.csv` — UTF-8 с BOM, разделитель запятая, заголовок в первой строке. Предварительно создать трекеры, категории, статусы и участников из таблиц. Добавить текстовые пользовательские поля `External ID`, `Depends on`, `Requirement`.

Открыть Задачи → меню → Импорт; выбрать файл, UTF-8, запятую, кавычку `"`. Сопоставить Subject→Тема, Tracker→Трекер, Status→Статус, Priority→Приоритет, Assigned to→Назначена, Estimated time→Оценка времени, Description→Описание, Category→Категория, остальные три — пользовательские поля. `Normal` сопоставить с обычным приоритетом своего языка интерфейса. Если версия не разрешает импорт конкретного поля статуса, задать `Новая` значением по умолчанию.

External ID вида SM-01 — стабильный проектный ключ, а не внутренний номер Redmine. После импорта проверить ровно 15 новых задач и исполнителей. Поле Depends on содержит проектные ключи; оно само не создаёт блокирующие связи. При ручном импорте по нему настроить связи «предшествует/следует» между созданными номерами. Автоматический bootstrap создаёт эти связи самостоятельно. Перед повторным импортом отфильтровать уже имеющиеся External ID, чтобы не создавать дубликаты.

Дерево целей: согласовать требования (SM-01–03) → подготовить среду и процесс (SM-04–07) → реализовать и проверить продукт (SM-08–14); отдельная индивидуальная инструментальная работа — SM-15. Проектные статусы в CSV намеренно начальные: факт генерации файла не означает импорт или закрытие задач в Redmine.

## 5 Приёмка и источники

Проверить вход под каждой ролью, недоступность чужих административных действий, переходы workflow и обратный переход после замечаний. Приложить скриншоты проекта, участников, workflow и списка из 15 задач. Источники: методичка ЛР №2, с. 21–36, 77–79; [импорт CSV Redmine](https://www.redmine.org/projects/redmine/wiki/HowTo_import_issues), [руководство Redmine](https://www.redmine.org/projects/redmine/wiki/Guide).

## 6 Проверенный результат

На локальном стенде работает Redmine 6.1.4, Ruby 3.4.10 и PostgreSQL 17.11. Проект supermarket-36 закрытый, в нём три участника, три трекера, 15 задач и 18 связей предшествования. Входы всех трёх участников проверены браузером: задачи доступны с HTTP 200, глобальное администрирование отклонено с HTTP 403. ЛР №4 назначена Роману Кочеткову.

Проверка redmine/verify.rb подтверждает отсутствие прямого перехода «Новая/В работе → Закрыта», наличие этапа ревью и уникальность ключей SM-01–SM-15. Все задачи остаются начальным бэклогом; автоматически закрывать результаты от лица участников не требуется. Почтовые уведомления отключены. При повторной настройке существующие задачи и пароли сохраняются.

Проверочный сценарий запускается через `docker compose --env-file .env -f redmine/docker-compose.yml exec -T redmine bundle exec rails runner -e production - < redmine/verify.rb`. Фактические снимки проекта и участников находятся в evidence/redmine-issues.png и evidence/redmine-members.png.
