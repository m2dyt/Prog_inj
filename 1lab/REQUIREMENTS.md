# Спецификация требований к информационной системе супермаркета

Версия требований 1.0. Предметная область — вариант 36. Статус документа на этапе ЛР №1: проектная спецификация. Приоритет Must обязателен для версии, Should — целевой критерий качества. Стабильность «высокая» относится к бизнес-правилам, «средняя» — к численным целям и интерфейсу.

| FR09 / UC05–06 | Идемпотентность создания и оплаты | Повтор UUID с тем же составом возвращает тот же чек; другой состав/автор — 409; повтор pay не создаёт второе движение |

### 2.1 Ограничения и бизнес-правила

1. R01: `price > 0`; деньги вычисляются десятичной арифметикой. В JSON суммы передаются строками, чтобы не зависеть от точности IEEE-754.
2. R02: остаток и количество целые; `stock ≥ 0`; весовой товар предварительно фасуется и учитывается упаковками.
3. R03: один штрихкод соответствует одной карточке, включая архив; повторное использование кода другой карточкой запрещено.
4. R04: черновик не резервирует товар. Между созданием и оплатой наличие может измениться; оплата повторно проверяет остаток и активность.
5. R05: цена фиксируется при создании черновика и сохраняется до завершения; последующие изменения каталога не меняют этот документ.
6. R06: `total = Σ(quantity × unit_price)`; клиент не передаёт итог, цену строки, статус, автора и время оплаты.
7. R07: оплата, движения и уменьшение остатков составляют одну транзакцию; при любой ошибке всё откатывается.
8. R08: допустимы только `draft → paid` и `draft → cancelled`; завершённые документы неизменны. Повтор запроса завершения читает существующий результат.
9. R09: строки чека не удаляются и не редактируются через публичный API; для исправления состава черновик отменяют и создают новый.
10. R10: карточки архивируются; ссылки из чеков и движений сохраняются. Физическое удаление исторических данных не является пользовательской функцией.
11. R11: ключ создания уникален; цена не входит в клиентский запрос, хеш определяется по отсортированным ID и количествам. Ключ повторяется при неизвестном результате сетевого запроса.
12. R12: кассир работает со своими чеками, менеджер — со всеми, аудитор выполняет только чтение. Администратор БД обслуживает пользователей вне API.

### 2.2 Внешние интерфейсы

Браузер обращается к серверу по HTTP/JSON под `/api`, в эксплуатации — через HTTPS на внешнем доверенном прокси. API использует Pydantic для схем, PostgreSQL — для транзакций и ограничений. Штрихкод вводится с клавиатуры; USB-сканер может работать как клавиатурное устройство. В первой версии автоматическое управление устройствами не требуется.

Ошибки: 401 — нет действующего сеанса; 403 — нет права; 404 — объект отсутствует или недоступен; 409 — конфликт данных/состояния; 422 — ошибка входных данных; 503 — временная недоступность. Сообщения не раскрывают SQL и пароли. Полный каталог не загружается для локальной фильтрации.

## 3 Нефункциональные требования

Таблица 3 — Качество и условия проверки

| ID | Цель | Измерение и границы |
|---|---|---|
| NFR01 | Каталог 100 000 товаров, не менее 100 000 чеков с несколькими строками | Синтетический набор в отдельной тестовой БД; реальные объёмы индексов фиксируются отдельно |

| NFR05 | Ограниченное потребление ресурсов | Максимум 100 строк выдачи и 100 строк чека; пул до 10 соединений на процесс API; тело HTTP до 128 КБ |
| NFR06 | Разграничение доступа | Отрицательные проверки всех изменяющих маршрутов; роль API без DDL и без удаления товаров/чеков |
| NFR07 | Сохранность при аварии | Транзакции PostgreSQL/WAL; целевые RPO 24 ч, RTO 60 мин при ежедневной копии и проведённом восстановлении |
| NFR08 | Воспроизводимость | Зафиксированные зависимости Python/JS, контейнерные файлы и сценарии запуска; изменение версии проходит проверку |
| NFR09 | Доступность интерфейса | Клавиатура, подписанные поля, видимый фокус, состояния загрузки/ошибки/пустого результата, отсутствие выхода содержимого за экран |
| NFR10 | Наблюдаемость | HTTP-журналы и health; секреты и тело входа не пишутся в журналы; постоянные ошибки исследуются по логам контейнера |

NFR02–03 и RPO/RTO — цели приёмки, не гарантии и не результаты измерений на этапе проектирования. В учебной конфигурации один экземпляр БД и API; высокая доступность и автоматическое переключение не заявлены.

### 3.1 Информационные требования к UI

UI01: карточка показывает название, штрихкод, категорию, цену за штуку, остаток и доступность добавления. UI02: корзина показывает название, количество, цену и предварительный итог; после создания чека отображается серверная сумма. UI03: история показывает ID, время, статус; детализация — строки и итог. UI04: профиль показывает сотрудника и роль; пароль не отображается открытым текстом.

### 3.2 Функциональные требования к UI

UI05: поиск имеет задержку 300 мс и отменяет устаревший запрос; ответ старого запроса не заменяет новый. UI06: переход вперёд/назад не накапливает весь каталог. UI07: во время отправки кнопка блокируется; при неизвестном исходе создания корзина фиксируется до повтора с тем же ключом. UI08: подтверждение наличных явно отделено от формирования чека. UI09: диалог редактирования управляет фокусом и закрывается Escape; ошибки не очищают введённые поля. UI10: PropTypes проверяют контракты компонентов при разработке, а проверка ответа API действует также в production.

Отсутствие D для товаров и документов осознанно: товар архивируется (U), оплаченный чек и движение сохраняются. Сотрудника создаёт администратор, поэтому в матрице есть источник C, хотя Web-формы управления сотрудниками нет. Начальная загрузка товаров относится к UC03, начального остатка — к UC04. Каждая сохраняемая сущность имеет сценарий создания и чтения.

## 5 Заключение и выводы

1. Требования сформулированы через наблюдаемые результаты и коды ошибок.
2. Сохранение истории и безопасная повторная отправка обязательны даже в учебной версии.
3. Пользовательские роли и роли СУБД выполняют разные задачи и проверяются отдельно.
4. Производительность подлежит измерению на указанном объёме, а не объявляется доказанной наличием индекса.
