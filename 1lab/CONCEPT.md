# Концепция и границы информационной системы супермаркета

## 1 Описание предметной области

Рассматривается один супермаркет с общим каталогом и остатком товаров, несколькими рабочими местами кассиров и рабочим местом менеджера. Менеджер ведёт карточки товаров, задаёт розничные цены, регистрирует поступления и корректировки остатка. Кассир находит товар по названию или полному штрихкоду, формирует чек и подтверждает получение наличных. Аудитор просматривает каталог и историю продаж.

Объект автоматизации — согласованная обработка товарных данных и кассовых продаж. В исходном организационном сценарии каталог и складской учёт ведутся раздельно. Кассир может видеть устаревшую цену, а две кассы — одновременно считать доступным последний экземпляр товара. Это проектная постановка проблемы, а не результат проведённого обследования реального магазина.

Внутренние участники: менеджер, кассир, аудитор, администратор БД. Покупатель участвует в бизнес-процессе, но не входит в интерфейс сотрудников. Банк и фискальный оператор находятся за границами учебного продукта. Учебный чек фиксирует внутреннюю продажу и не является интеграцией с кассовым фискальным устройством.

## 2 Цель и постановка задачи

Цель — создать единый источник товарных данных и обеспечить согласованность чека с движением остатка при параллельной работе кассиров.

Задачи проектирования:

1. Зафиксировать словарь сущностей, диапазоны значений и правила изменения данных.
2. Определить пользовательские сценарии и доступ к ним по ролям.
3. Исключить отрицательные остатки, повторное списание и изменение завершённых чеков.
4. Спроектировать поиск и ограниченную постраничную выдачу для каталога около 100 тысяч объектов.
5. Разделить интерфейс, бизнес-логику и хранение данных в клиент-серверной архитектуре.

Ожидаемый эффект: кассир использует актуальный единый каталог; цена и наименование сохраняются в строке чека; продажа либо целиком фиксируется вместе со списанием, либо не изменяет состояние БД. Измеримые критерии приёмки содержатся в спецификации.

### 2.1 Границы первой версии

Включаются: вход сотрудников, каталог, поиск, управление карточками, архивирование, корректировка остатков с основанием, черновик чека, оплата наличными, отмена черновика, просмотр истории и настройка инфраструктуры. Рабочая единица количества — штука; фасованные продукты продаются упаковками.

За границами версии: весовые товары с дробным количеством, возвраты оплаченных чеков, скидочные программы, эквайринг, фискализация, поставщики и закупочные заказы, учёт партий и сроков годности, несколько магазинов, автономная касса при потере сети. Такие расширения требуют изменения требований и схемы данных.

## 3 Словарь данных предметной области

Запись составляется знаком `+`; необязательное поле заключено в круглые скобки; `1:100{Строка чека}` означает от одной до ста строк. Примитивы таблицы 1 определяют диапазоны структур таблицы 2.

Таблица 1 — Элементы данных

| Элемент | Значение и тип | Ограничение |
|---|---|---|
| Идентификатор | Положительное целое, BIGINT | Генерируется БД; в API не больше 2^53−1 для точного JS Number |
| Штрихкод | Строка | 8–14 ASCII-цифр; уникален; ведущие нули сохраняются; контрольная цифра в этой версии не проверяется |
| Название | Строка Unicode | 2–160 символов после удаления пробелов по краям |
| Категория | Строка Unicode | 2–60 символов; текстовое поле справочника карточек |
| Цена | Десятичное число | 0,01–999999,99 руб.; максимум два знака после запятой |
| Остаток | Целое | 0–1 000 000 000 шт. |
| Количество в строке | Целое | 1–10 000 шт.; один товар один раз в чеке |
| Изменение остатка | Целое со знаком | Для ручной операции −1 000 000…1 000 000, кроме 0 |
| Основание | Строка Unicode | 5–200 символов |
| Статус чека | Перечисление | draft, paid, cancelled |
| Время | Дата и время с часовым поясом | Хранение timestamptz; показ в локальном времени браузера |
| Версия карточки | Положительное целое | Увеличивается при изменении карточки или остатка |
| Логин | Строка | 3–50 символов; первая латинская строчная буква, далее буквы, цифры, `_` |
| Роль сотрудника | Перечисление | manager, cashier, auditor |
| Ключ запроса | UUID | Идентифицирует одну попытку создания чека, включая повторы |
| Хеш содержимого | SHA-256 | Позволяет обнаружить повтор ключа с другой корзиной |
| Хеш пароля | Строка | Алгоритм scrypt, индивидуальная соль; открытый пароль не хранится |
| Сессия | Случайный токен | В БД хранится только SHA-256 токена; срок жизни 8 часов |

Таблица 2 — Структуры данных

| Структура | Состав | Назначение |
|---|---|---|
| Товар | ID + Штрихкод + Название + Категория + Цена + Остаток + Активность + Версия + Время изменения | Единица каталога и складского учёта |
| Сотрудник | ID + Логин + Отображаемое имя + Хеш пароля + Роль + Активность | Идентификация и разграничение доступа |
| Чек | ID + Ключ запроса + Хеш содержимого + ID кассира + Статус + Время создания + (Время оплаты) + 1:100{Строка чека} | Документ продажи |
| Строка чека | ID чека + ID товара + Снимок названия + Снимок штрихкода + Количество + Снимок цены + Сумма | Исторически неизменный состав покупки |
| Движение остатка | ID + ID товара + ID сотрудника + (ID чека) + Изменение остатка + Основание + Время | Объяснение увеличения или уменьшения остатка |
| Сеанс | Хеш токена + ID сотрудника + Время истечения | Временный доступ к API |

Итог чека определяется как сумма произведений количества на зафиксированную цену. Он не поступает от браузера и не является самостоятельно редактируемым реквизитом.

## 4 Нежелательные эффекты и конфликты

Обозначения из методички: `+` — конфликт, `−` — отсутствие конфликта, `·` — связь не рассматривается. Сравниваются подсистемы исходного процесса.

Таблица 3 — Матрица взаимодействий

| Элемент | Каталог цен | Касса А | Касса Б | Остаток | История |
|---|---|---|---|---|---|
| Каталог цен | · | + | + | − | + |
| Касса А | · | · | + | + | + |
| Касса Б | · | · | · | + | + |
| Остаток | · | · | · | · | + |
| История | · | · | · | · | · |

Таблица 4 — Причины и способы устранения конфликтов

| Код | Конфликт и нежелательный эффект | Проектное решение |
|---|---|---|
| C1 | Каталог и касса: цена изменилась во время подбора | Браузер показывает предварительный итог; сервер фиксирует цену при создании черновика |
| C2 | Две кассы и общий остаток: продажа последнего экземпляра дважды | Блокировка товарных строк в порядке ID и повторная проверка в транзакции оплаты |
| C3 | Каталог и история: изменение карточки меняет прошлый чек | Снимки реквизитов в строках чека; запрет изменения завершённого документа |
| C4 | Касса и история: потерян ответ сети, кассир повторил действие | Уникальный ключ создания; повтор оплаты возвращает существующий результат |
| C5 | Остаток и история: списание прошло, а чек не сохранился | Чек, движения и остатки меняются в одной транзакции |
| C6 | Скорость поиска и объём данных: загрузка 100 тысяч карточек перегружает браузер | Индексы, серверный поиск и курсорная пагинация |
| C7 | Простота доступа и целостность: кассир меняет цены | Аутентификация и проверка роли на сервере; ограничения роли БД |

## 5 Варианты использования

UC01 — войти и завершить сеанс; UC02 — найти и просмотреть товар; UC03 — вести карточку и архив; UC04 — изменить остаток; UC05 — сформировать чек; UC06 — подтвердить оплату наличными; UC07 — отменить черновик; UC08 — просмотреть историю и состав чека; UC09 — администрировать пользователей БД и резервное копирование.

UC02 доступен всем сотрудникам; UC03–04 — менеджеру; UC05–07 — кассиру и менеджеру; UC08 ограничивает кассира собственными чеками, менеджеру и аудитору доступна вся история. UC09 выполняет администратор БД вне пользовательского Web-интерфейса. Модель UC — рисунок 1 в DOMAIN_MODEL.md, CRUD — таблица 4 в REQUIREMENTS.md.

## 6 Дерево функций

```text
ИС супермаркета
├── F1 Управление доступом (UC01)
│   ├── Проверить пароль и активность
│   └── Выдать, проверить и отозвать сеанс
├── F2 Ведение товарных данных (UC02–04)
│   ├── Найти товар и перейти к следующей странице
│   ├── Создать или изменить карточку
│   ├── Архивировать карточку
│   └── Зарегистрировать движение остатка
├── F3 Обслуживание продажи (UC05–07)
│   ├── Сформировать корзину
│   ├── Зафиксировать цены в черновике чека
│   ├── Проверить остатки и подтвердить оплату
│   └── Отменить неоплаченный документ
├── F4 Контроль продаж (UC08)
│   ├── Выдать историю по правам сотрудника
│   └── Показать строки, статус и итог чека
└── F5 Эксплуатация (UC09)
    ├── Проверить доступность компонентов
    ├── Управлять пользователями и правами БД
    └── Создать и проверить резервную копию
```

Каждый лист связан с вариантом использования. F2 устраняет C1/C6, F3 — C2/C4/C5, F4 — C3, F1/F5 — C7 и эксплуатационные риски.

## 7 Заключение и выводы

1. Центральная сущность продажи — чек со строками, а не отдельная запись товара.
2. Историческую цену необходимо отделить от текущей цены каталога.
3. Управление остатком и фиксация оплаты должны иметь общую транзакционную границу.
4. Объём 100 тысяч объектов требует ограничения выдачи, но сам по себе не обосновывает распределённую БД.
5. Границы учебной версии позволяют проверить основные правила без внешних платёжных и фискальных интеграций.
