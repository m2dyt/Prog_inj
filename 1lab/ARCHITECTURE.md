# Архитектура программного обеспечения

## 1 Вариант архитектуры и обоснование

Выбрана трёхуровневая клиент-серверная архитектура: React-клиент в браузере, FastAPI-сервер приложений, PostgreSQL. Nginx отдаёт статические файлы и проксирует `/api`. Предметные функции объединены в модульный монолит: для одной команды из трёх человек это позволяет сохранять продажу одной транзакцией и не вводить распределённые транзакции.

### 1.1 Модульная структура

Таблица 1 — Модули, методы и данные проектируемой системы

| Модуль | Назначение и методы в псевдокоде | Данные и зависимости |
|---|---|---|
| Auth | login(credentials), me(token), logout(token), requireRole(role) | Сотрудник, сеанс; использует Security и DB |
| Security | hashPassword(password), verifyPassword(password, hash), hashToken(token) | Соль и хеш; не зависит от UI |
| Catalog | list(query,cursor,limit), create(card), update(card,version) | Товар; использует Auth, Validation, DB |
| Inventory | adjust(product,delta,reason), recordMovement(...) | Остаток и движение; использует Auth, DB |
| Sales | createReceipt(key,lines), pay(id), cancel(id), read(id), history(cursor) | Чек, строка; использует Auth, Catalog/Inventory через общую транзакцию |
| Validation | validateProduct(...), validateReceipt(...) | Схемы запросов; ограничивает типы, диапазоны и повтор товаров |
| DB | acquireConnection(), begin(), commit(), rollback() | Пул соединений и параметризованные SQL-запросы |
| Web Catalog | search(), nextPage(), addToCart(), editCard() | Состояние фильтра, текущая страница; вызывает API-client |
| Web Checkout | prepare(), confirmCash(), cancelDraft() | Корзина, серверный чек, ключ повтора |
| API-client | request(path,body,token), validateResponse(...) | JSON, отмена запроса, преобразование ошибок |

Декомпозиция по функциям; наследование не служит основным способом организации приложения. Схемы запросов могут наследовать общие правила Pydantic. React-компоненты составляются композиционно и используют хуки.

### 1.2 Компоненты и соединители

Браузер инициирует HTTP-запросы; Nginx отдаёт сборку и передаёт API-запросы FastAPI. Сервер выполняет аутентификацию, валидацию и бизнес-правила, затем обращается к БД по PostgreSQL wire protocol. Совместно используемые данные находятся только в PostgreSQL. UI не открывает соединение с БД.

Параллелизм: несколько браузеров и несколько обработчиков API используют общий пул. При оплате сервер блокирует чек, затем товары в возрастающем порядке ID. Такой порядок уменьшает возможность взаимоблокировки. Строки разных товаров допускают параллельные продажи; конфликт за последний экземпляр разрешается БД. READ COMMITTED с блокировками достаточен для выбранной транзакции; повторная проверка после получения блокировки обязательна.

Псевдокод оплаты: проверить сеанс → начать транзакцию → заблокировать чек → вернуть результат, если уже paid → проверить draft → заблокировать товары по ID → проверить остаток и активность → уменьшить остаток → создать движения → пометить paid → commit. Ошибка на любом шаге приводит к rollback. Сетевой ответ отправляется после фиксации транзакции.

## 2 Структуры распределения

### 2.1 Размещение

Рисунок 6 — `diagrams/06-deployment.puml`. Рабочая станция кассира выполняет браузер. Linux VM выполняет Nginx, FastAPI и PostgreSQL в отдельных контейнерах. Том БД сохраняется между перезапусками. База и API не публикуют порты на внешний интерфейс; доступ к приложению в учебном стенде ограничен localhost. Для доступа из локальной сети адрес публикации и TLS настраиваются отдельно.

Проектная VM: 4 vCPU, 8 ГБ RAM, 40 ГБ диска с возможностью расширения; гостевая ОС Linux, сеть NAT с ограниченным пробросом или host-only. Производительность проверяется измерением на реальном выделенном стенде. Контейнеры не заменяют этап установки VM, предусмотренный ЛР №2.

## 3 Надёжность и эксплуатационные границы

Блокировки обеспечивают согласованность между экземплярами API, а не только внутри одного процесса. Размер пула ограничивает число соединений. Запросы имеют таймаут; занятый сервис отвечает временной ошибкой, которую клиент может повторить. Отсутствие сети не разрешает клиенту списывать остатки самостоятельно.

Секреты передаются через локальный конфигурационный файл, не включаются в сборку клиента и Git. Различаются пользовательские роли приложения и технические роли БД. Администратор БД доверенный и может обходить прикладные ограничения; его действия выполняются по регламенту. Контур приложения и контур Redmine имеют разные базы и тома.

## 4 Заключение и выводы

1. Три уровня разделяют отображение, принятие решений и сохранение данных.
2. Модульный монолит соответствует размеру команды и общей транзакции продажи.
3. Структуры размещения, реализации и распределения обязанностей описывают разные стороны одной архитектуры.
4. Масштабирование начинается с корректных запросов, индексов и ограниченных ответов; отдельные сервисы вводятся только при подтверждённой необходимости.
