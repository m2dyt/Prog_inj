# Проверка ЛР №3

## Серверные интеграционные тесты

Тесты используют настоящую PostgreSQL, а не SQLite. Нужна отдельная БД с именем, заканчивающимся `_test`, и схема `init.sql`. На сервере с несколькими тестовыми базами учитывать, что роли PostgreSQL относятся ко всему кластеру: создавать их один раз, а дальнейшие схемы восстанавливать из проверенной копии.

`DATABASE_URL` — строка подключения market_app, `TEST_ADMIN_URL` — market_admin в той же отдельной базе. Передать секреты через окружение. Из `backend`:

```bash
python -m unittest discover -s tests -v
```

Без переменных тесты явно пропускаются и не означают успешную интеграционную проверку. Fixture создаёт пользователей `test_manager`, `test_cashier`, `test_auditor` и меняет только их пароли в `_test`-БД. Товары имеют случайные штрихкоды; существующие таблицы не очищаются. После тестирования временный стенд можно удалить целиком отдельно от рабочих данных.

Проверяются: аутентификация/выход, роли, некорректные деньги и количества, чужие поля, пустой и дублированный состав, ограничение пагинации, SQL-подобная строка поиска, повтор UUID, повтор pay, снимок цены, конкуренция за последний товар, переходы состояний, архивирование, конфликт версии карточки и ограниченные SQL-права.

## Проверки клиента

Из `frontend`: `pnpm test`, `pnpm build`. Тесты проверяют отключение добавления при отсутствии остатка, обработку и повтор сетевой ошибки, курсорный запрос и замену страницы, некорректный JSON и истечение сеанса. Дополнительно проверить браузером вход, каталог, корзину, менеджерскую карточку, историю и размеры 390/768/1440 px. Пройти элементы Tab/Shift+Tab; в диалоге Escape должен закрывать форму.

## Нагрузочный набор и измерения

В отдельной `_test` или `_bench` БД после начальной загрузки выполнить `db/seed_large.sql`, затем `db/explain.sql`. Записать actual time, buffers и выбранные индексы. Для полного HTTP-профиля 20 конкурентных пользователей измерять p50/p95 и долю ошибок отдельно от SQL. Один EXPLAIN не подтверждает NFR02–03. Нельзя измерять все 100 тысяч объектов в браузере — это нарушает сам контракт пагинации.

## Системная интеграция

Проверить `docker compose config --quiet`, готовность db/api, успешное завершение bootstrap, выдачу статических файлов и `/api/health` через Nginx, повторный запуск с сохранением данных. Проверить резервную копию и восстановление по DATABASE.md. Сохранить собственные скриншоты; протокол фактически выполненных сейчас проверок вынесен в `../VERIFICATION.md`.

## Автоматический отдельный тестовый стенд

После `bash setup.sh --check` выполнить `bash verify.sh`. Файл compose.test.yml запускает собственную PostgreSQL supermarket_test и серверные тесты без публикации портов. Имя Compose-проекта уникально для запуска; trap удаляет только его временные контейнеры и тома. Прикладной db_data остаётся отдельным. Fixture проверяет совпадение подключения API и администратора с одной тестовой БД до первой записи.

Повторная проверка 08.09.2026: 8 серверных тестов прошли за 16,874 с на PostgreSQL 17.5 Windows с большим набором данных; 5 тестов клиента и сборка Vite прошли. В Linux Docker отдельно проверена инициализация init.sql на PostgreSQL 17.11: созданы все шесть таблиц market, включая ICU-индекс. Образ React/Nginx собран штатным Dockerfile.
